# Task 1.5.4 – Local notifications: permissions, Android channels, iOS setup

## Goal

Every alert the engine raises (1.5.3) appears as a phone notification, in words from the ARB, when the user has Notifications on and the phone allows it. Tapping one opens the Alerts tab. A new user is asked for the permission once, after logging in.

## Requirements covered

- 7.2 Show alerts as phone notifications (and in an Alerts list, 1.5.5).
- 7.3 Sample alerts: "Heart rate above 110 bpm", "CO₂ above 1,000 ppm", "Battery low (12%)", "Missed 3 heartbeats – device offline".
- 9 Profile: the Notifications switch.
- Architecture: Notifications are local in both phases, from the config conditions (`AlertEngine`).

## Scope

**In scope**

- **Notifier**: `LocalNotificationsNotifier` implements `AlertNotifier` with `flutter_local_notifications`.
  - It shows each raised alert, using the alert's stored id as the notification id.
  - It shows nothing when the user's Notifications setting is off, the phone's permission is not granted, or the device has been removed.
  - Errors are caught; only their type is logged (debug), never the text, which holds health values.
- **Text** (ARB, `alert…` keys), as in the mockup:
  - Title by kind: "{reading} above {limit}", "{reading} below {limit}", "Battery low ({percent})", "Missed {count} heartbeats – device offline".
  - Body: "{device} · now {value}" for readings and battery, "{device}" for offline.
  - Reading labels, units and decimals come from the device's profile; the missed count from its heartbeat settings.
- **Android channels**: "Reading alerts" (above / below) and "Device alerts" (battery low, offline), both high importance so every alert pops up (decision 2026-11-20), with ARB names and descriptions, so a user can mute either in the phone's settings. A white bell icon (`@drawable/ic_notification`), kept in release builds (`res/raw/keep.xml`).
- **iOS**: the notification-center delegate is set in `AppDelegate`, so notifications also show while the app is open and taps reach the app.
- **Lock screen**: full text, values included (decision 2026-11-19).
- **Tap**: opens the Alerts tab, also when the tap launched the app.
- **Permission once after login**: when the logged-in screens first show, if Notifications is on and the phone has not been asked yet, the app asks. Refused (or blocked earlier), the setting turns off so Profile shows the truth; the Profile switch can ask again. This happens after the login screen's Face ID offer, and also after registration and for a restored session.

**Out of scope**

- The Alerts list, mark all read and the tab badge (1.5.5).
- Notifications while the app is closed (background Bluetooth is not set up).
- Scheduled notifications, custom sounds, notification actions.

## Acceptance criteria

- [x] A raised alert shows as a notification with the mockup's wording, in the right Android channel.
- [x] Nothing shows with Notifications off, without the permission, or for a removed device.
- [x] Tapping a notification opens the Alerts tab (app running or launched by the tap).
- [x] A new user is asked once after login; refused, the setting shows off.
- [x] iOS shows notifications while the app is open.
- [x] No notification text or values in logs.
- [x] Unit tests added (mocktail, table-driven text); `flutter analyze` and `flutter test` are clean.
- [ ] Checked on a phone (Android 13+ and iPhone; a release build shows the icon).
