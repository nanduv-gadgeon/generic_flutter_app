# Task 1.5.3 – Alert engine from config conditions (limits, low battery, offline)

## Goal

The phone raises an alert when a connected device's reading crosses one of its limits, its battery runs low, or it goes Offline after missed heartbeats. Each alert is stored on the phone for the Alerts list and Home's count, and is handed to a notifier hook that 1.5.4 turns into a phone notification.

## Requirements covered

- 7.1 Alerts are raised on the phone in both phases, from the alert conditions in the config file for each device type: a reading crossing a limit, low battery, or a device going offline (missed heartbeats).
- 10.5 After the set number of missed heartbeats the device is marked Offline and a "Device offline" alert is raised.
- Architecture: `AlertEngine` (Notifications row); `alerts` table (the local alerts list); data kept on the phone for `history.daysOnPhone` days.

## Scope

**In scope**

- **Conditions**, from each device's `DeviceAlerts` rows (copied from the profile's `alerts` when the device was added; Device settings turns each on or off):
  - `above` / `below` a limit, for any reading key of the profile;
  - **Low battery**: the `battery` key with `below`;
  - **Offline**: the heartbeat monitor's Online → Offline change (`offlineAfterMissed` × `intervalSeconds` from the profile).
  - A limit turned off raises nothing. A turn on or off takes effect at once.
- **Once per crossing** (de-duplication):
  - An alert is raised when the value crosses its limit. It is not raised again while it stays over the limit, only after the value has gone back inside it.
  - Low battery: while the battery stays below its limit, each new whole-percent low raises another alert, so 14 → 13 → 12 raises three, while 14 → 13 → 14 → 13 raises two. Each one is its own notification; they stack (decision 2026-11-19). It starts over once the battery has risen to its limit + 5.
  - Offline is raised once, and again only after the device has been Online.
  - The open state is kept in memory: after an app restart a reading still over its limit raises once more.
- **Which devices:** only the connected device is monitored (decision 2026-11-15). A device the user disconnected is never Offline, so it raises no Offline alert (decision 2026-11-18). The engine never connects a device itself.
- **Storage:** the new `raised_alerts` table (schema v8): device, kind, reading key, value, limit, time, read. The repository watches a user's alerts newest first, counts unread ones and marks all read. Alerts are deleted with their device, and by the daily cleanup job after `history.daysOnPhone` days.
- **Home:** "open alerts" shows the unread count.
- **Notifier hook:** every raised alert goes to `AlertNotifier.show`. In this task it does nothing (`NoAlertNotifier`, `TODO(1.5.4)`).
- `features.alerts` false: no alerts are raised.
- The engine stores facts (kind, key, value, limit), never sentences. The words come from the ARB in 1.5.4 / 1.5.5.

**Out of scope**

- Phone notifications, their permission, Android channels and iOS setup (1.5.4).
- The Alerts list screen, mark all read button, tab badge and alert on/off switches (1.5.5).
- Background monitoring while the app is closed (background Bluetooth is not set up).
- Phase 2 cloud alerts or syncing alerts.

## Acceptance criteria

- [x] A reading crossing an enabled limit stores one alert; staying over the limit stores no more; going back inside and crossing again stores another.
- [x] Battery below its limit stores an alert at each new whole-percent low; it starts over only after rising 5 above the limit.
- [x] A device going Offline stores one alert; a disconnected device never does.
- [x] A limit turned off raises nothing; `features.alerts` false raises nothing.
- [x] Every raised alert is passed to `AlertNotifier`.
- [x] Alerts are deleted with their device and after `history.daysOnPhone` days; Home shows the unread count.
- [x] Schema v8 migration with its test; nothing in `drift_schemas/` edited by hand.
- [x] No reading values in logs.
- [x] Unit tests added (mocktail, table-driven rules and de-duplication); `flutter analyze` and `flutter test` are clean.
- [ ] Checked on a phone (a dummy device over its limit; a real device switched off).
