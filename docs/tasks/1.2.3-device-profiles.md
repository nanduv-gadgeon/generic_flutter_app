# Task 1.2.3 – Device profile registry from the config file

## Goal

The app reads the device profiles from the config file, checks them at start-up, and gives later tasks one place to look up a device type. Adding a device type is a config change, not a code change.

## Requirements covered

- 4.1 Add device step 1: the list of device types comes from the config file.
- Config file, "Device types" and "Alert conditions" rows; "Device data in V1" readings and default alerts.
- Quality: automated tests for each device profile.

## Scope

**In scope**

- A minimal profile shape: `id`, `label`, `summary`, `icon`, `transports`, `readings` and `alerts`.
- Schema rules for the profile, and cross-checks the schema cannot express.
- `DeviceProfileRegistry`: profiles offered (in `deviceTypes` order) and lookup by id.
- VitaCare profiles: the 4 mockup types and `ief_device_v1`.

**Out of scope** (each section is added by the task that first needs it)

| Section | Task |
| --- | --- |
| `ble` (service and characteristic UUIDs, scan filter) | 1.2.4 |
| `packet` (frame, fields, checksum) | 1.2.5 |
| `wifi` (setup method, discovery, stream) | 1.2.6 |
| `heartbeat` (interval, missed before Offline) | 1.2.8 |
| `commands` (device action buttons) | 1.2.4 / 1.3.6 |
| `dashboard` (main reading, tile order, scale) | 1.3.5 |

## Interfaces / files expected

| File | Layer | Purpose |

## Phase behaviour

| isCloud | Behaviour |
| --- | --- |
| false (Phase 1) | Profiles come from the bundled config only. No network calls. |
| true (Phase 2) | Same. Suggested alert settings from the cloud arrive in 1.2.7 and do not change the profile. |

## Open items

- `ief_device_v1`: the unit of `current` is assumed to be mA; confirm against firmware.
- `ief_device_v1`: the scan-filter UUID differs from the service UUID (see the protocol doc); settle in 1.2.4.
- `ief_device_v1` has no heartbeat packet; 1.2.8 decides whether battery notifications count as heartbeats.
- Protocol documents for the 4 mockup types are still to come.

## Acceptance criteria

- [x] Every bundled customer config passes the schema and `checkDeviceProfiles`.
- [ ] A bad profile (missing type, unknown alert key, duplicate key, bad range) stops start-up with a config error on the splash screen. Covered by loader tests; manual check on a simulator pending.
- [x] `offered` follows the `deviceTypes` order; profiles not listed there are not offered.
- [x] Unit tests added (table-driven for the checks); `flutter analyze` and `flutter test` are clean.
