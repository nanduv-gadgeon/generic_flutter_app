# Task 1.2.5 – Generic packet decoder (fields, scale, endian, checksum)

## Goal

Data received from any device is turned into readings and events by one generic decoder, following the profile's `packet` block, so a new device that fits the rules needs no Dart code. The reading pipeline (1.3.3) feeds BLE notifications into it.

## Requirements covered

- Config file, "Data decoding" row: packet layout (field, byte position, length, data type, scale, unit).
- Config file, "Device commands" row: the bytes each command sends.
- Quality: automated tests for the data decoder and each device profile, using sample packets.

## Scope

**In scope**

- Profile `packet` block (`lib/domain/models/packet_layout.dart`) with:
  - frame types picked by the first byte (`data`, `batchEnd`, `noData`) and a `minLength`
  - checksums `crc32`, `xor8`, `sum8` with a list of accepted forms (`from`, `to`, byte order); negative offsets count from the frame end
  - repeated `records` (`start`, `end`, `size`); bytes that do not fill a record are ignored
  - fields: `uint8/16/32/64`, `int8/16/32`, `float32`, byte order, `scale`, `when` condition; fields with the same key are added together
  - an optional per-record `time` (Unix `s` or `ms`), else the receive time
  - `events`: record types mapped to start, stop, error; other non-data types become unknown events
- `GenericCodec` and `codecFor(profile)` (`lib/domain/decoder/generic_codec.dart`), behind the `DeviceCodec` interface.
- Profile `commands` (`[{id, bytes}]`), sent with `encode(commandId)`.
- Start-up checks: fields, conditions, time and event offsets fit in a record (or `minLength`), every reading comes from a field, a BLE profile has a `packet`, unique frame codes and command ids.
- The IEF patch described in the VitaCare config from `docs/protocols/ief_device_v1.md`.
- The BLE link asks for MTU 517 after connecting, so a whole frame fits in one notification.

**Out of scope**

- Set clock (RTC) command and collecting frames until `0x91` with the 30 s timeout: 1.3.3.
- Wiring link → decoder → database: 1.3.3.
- `crc16`: added when a protocol document needs it (its variants differ by device).
- Packet blocks for the 4 mockup types (protocol documents still to come).

## Open items

- IEF big-endian CRC is read as applying to the entries-only CRC (3 forms, as listed in the protocol doc). If firmware also sends a big-endian whole-frame CRC, add a 4th `accept` entry in the config.
- Whether frames still arrive split after the MTU request: check in the real-device test.
- IEF current unit (mA) to confirm against firmware.

## Acceptance criteria

- [x] The VitaCare IEF profile decodes the protocol doc's sample frame to: DATA battery 85 %, current 30.07; ERROR battery 84 %, code 0x05, at the documented times.
- [x] All 3 documented IEF CRC forms are accepted; anything else is dropped as `InvalidPacket('checksum')` without its bytes.
- [x] Every field type, both byte orders, scale, records, conditions, same-key sums, time and each checksum type are covered by table-driven tests.
- [x] `encode('request_logs')` gives `82 00`.
- [x] A packet block that does not fit its records, or readings no field gives, stops start-up with a config error.
- [x] Unit tests added; `flutter analyze` and `flutter test` are clean.
- [ ] Real-device check: Request logs gives frames that decode with a valid CRC.
