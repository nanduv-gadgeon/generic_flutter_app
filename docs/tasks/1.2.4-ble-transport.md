# Task 1.2.4 – BLE transport: scan, connect, bond, notify, write commands, auto-reconnect

## Goal

The app can find a device of a configured type over Bluetooth LE, connect (and pair if the profile asks), receive its data and battery level, send it commands, and reconnect by itself after the link drops. Add device (1.2.7), the decoder (1.2.5) and the heartbeat monitor (1.2.8) build on it.

## Requirements covered

- 4.2 Add a device: Bluetooth scan of nearby devices; connection details come from the device type in the config file.
- Config file, "Connection" and "Device commands" rows: BLE service and characteristic IDs, scan name filter, command bytes.
- Architecture, "Device communication": BLE connect, BLE data, BLE commands, reconnect with backoff 2, 5, 15, 60 s.
- Security design, "Devices": only devices matching a profile are found; bonding where supported.

## Scope

**In scope**

- `universal_ble` instead of `flutter_blue_plus` (licence; see decisions).
- Android and iOS Bluetooth permissions.
- Profile `ble` block (optional) and `commands` list: schema, model, checks.
- `DeviceLink`, `BleScanner` and `ReconnectBackoff` in `lib/domain/transport/`.
- `BleAdapter` (thin wrapper over the package), `BleDeviceLink` and `BleScannerImpl` in `lib/data/transports/ble/`.
- Providers in `lib/core/di/transports.dart`.
- The IEF wearable patch `ble` block and `request_logs` command from its protocol doc.

**Out of scope**

- Commands built from values, such as the IEF time sync (RTC): 1.2.5.
- Fetching the IEF log backlog (multi-frame sync): 1.3.3.
- Wi‑Fi (1.2.6), screens (1.2.7), heartbeat and offline rules (1.2.8), unpairing on Remove device (1.2.11).
- iOS background BLE.

## Open items

- `ief_device_v1`: scan filter UUID `00001257-dd10-…` vs service UUID `1257dd10-…`. The profile keeps both (`scanServiceUuid`, `serviceUuid`); check with a real device which one it advertises.
- `ief_device_v1`: the RTC (time sync) command needs value encoding (1.2.5).
- The 4 mockup types have no `ble` block until their protocol documents arrive; they cannot connect yet.

## Acceptance criteria

- [x] A scan only reports devices advertising the profile's scan service or name prefix, and stops after its timeout.
- [x] Connect fails with `LinkException` and leaves the device disconnected when the service or a characteristic is missing.
- [x] Packets and battery (read, then notifications) are passed on and never logged.
- [x] A failed write is retried once after 100 ms.
- [x] After a drop the link reconnects with waits of 2, 5, 15, then 60 s, until `disconnect()`.
- [x] Unit tests added (mocktail, table-driven where there are cases); `flutter analyze` and `flutter test` are clean.
- [ ] Manual check with a real IEF device: scan, connect, battery, `82 00` gets `0x90`/`0x91`/`0x92`, reconnect after power cycle.
